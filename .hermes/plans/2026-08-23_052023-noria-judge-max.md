# Noria Judge-Max v1 — One-Shot Build Plan

> This supersedes the earlier MVP-only and broad full-product plans. It keeps the high-impact judge features and restores the practical MVP features needed for a usable product.

## Goal

Build a real, publicly accessible Noria v1 that helps users discover, understand, compare, activate, and manage autonomous agents on BNB Smart Chain.

## Product thesis

Noria is the intelligent discovery and trust layer around BNB Agent Studio:

```text
User goal → real agent discovery → evidence → comparison → bounded activation → mission receipt
```

No fabricated agents, reputation, performance, transactions, permissions, or success states.

---

## Final scope

### Core judge-facing features

- AI Agent Concierge for natural-language goals
- Four equal categories:
  - Rebalancing
  - Grid trading
  - Yield optimisation
  - Health-factor monitoring
- Real 8004scan/ERC-8004 agent discovery
- Deterministic search, filtering, and explainable fit ranking
- Real New and Trending dashboards based only on available source fields
- Agent Passport pages
- Evidence/Proof Mode
- Comparison Lab for 2–3 agents
- Evidence-backed pros and cons
- One real BSC testnet activation/hiring path
- Permission preview before activation
- Real transaction/result proof
- Mission Receipt after completion

### Restored practical MVP features

- Lightweight Supabase authentication
- Saved agents
- Saved searches
- Saved comparisons
- Basic user preferences
- Mission Builder
- Active Missions dashboard
- Mission state machine:
  - Draft
  - Awaiting approval
  - Active
  - Completed
  - Failed
  - Paused/revoked where supported
- Permission history
- Pause/revoke controls where supported
- Activity timeline
- Public deployment and clean demo path

### Small operational surfaces required to make the above real

- Server-side ingestion refresh route
- Source health/status panel for the build team
- Admin-only record review for invalid/duplicate records
- Integration feature flags
- Audit events
- Error and unavailable-data states

These are operational necessities, not a full separate admin product.

---

## Explicitly out of this build

- Native mobile app
- Multi-chain support
- Full creator marketplace onboarding
- Creator analytics
- Multi-agent orchestration
- Agent-to-agent commerce
- Subscriptions
- Escrow
- Disputes/refunds
- DAO/team accounts
- Enterprise permissions
- Public developer API/SDK
- Unrestricted autonomous trading
- Any simulated transaction or fake metric

These can be future product phases, but do not enter the one-shot implementation unless a real integration is already proven and the addition clearly improves judging.

## Exact build order

### Phase 1 — Repository and environment

1. Use `https://github.com/DeathThe27th/noria`.
2. Configure Next.js/TypeScript and MonSkills-inspired frontend structure.
3. Add `.env.example` with names only.
4. Verify GitHub, Vercel, Gemini, 8004scan, and Supabase without printing secrets.
5. Keep service-role/API keys server-side.
6. Create the first clean baseline commit and push.

### Phase 2 — Live data contract

1. Read the hackathon-provided resources first.
2. Inspect 8004scan developer docs and live endpoints.
3. Pull real agent records.
4. Identify actual identity, capability, reputation, feedback, activity, timestamp, and protocol fields.
5. Mark unsupported fields as unavailable.
6. Define the truthful data contract before UI claims.

### Phase 3 — Supabase schema and ingestion

1. Create normalized agent/source/activity/reputation tables.
2. Add profile, saved-item, comparison, mission, permission, transaction, and audit tables.
3. Implement server-side 8004scan client.
4. Normalize/deduplicate/cache real data.
5. Preserve source links and retrieval timestamps.
6. Add refresh/error handling.
7. Verify the first real data load.
8. Commit and push the working data slice.

### Phase 4 — First testable vertical slice

Build and deploy as early as possible:

1. Home/discovery page
2. Real BSC agent cards
3. Category filters
4. Agent Passport page
5. Source/evidence links
6. New/trending views only where data supports them

Deploy the first Vercel preview immediately after this passes.

**This is the first point where the user can begin testing.**

### Phase 5 — Deterministic discovery engine

1. Search by name, capability, category, protocol, and evidence.
2. Add structured fit scoring.
3. Make every score explainable.
4. Add insufficient-evidence states.
5. Add stable sorting and pagination.
6. Test ranking against real records.
7. Commit and push.

### Phase 6 — AI concierge

1. Define strict JSON intent schema.
2. Use Gemini server-side for intent parsing.
3. Validate every response.
4. Ask clarifying questions only when necessary.
5. Pass validated intent to deterministic ranking.
6. Generate pros/cons only from verified shortlisted fields.
7. Add provider timeout and fallback handling.
8. Commit and push.

### Phase 7 — Comparison and proof experience

1. Build Comparison Lab.
2. Add side-by-side cards.
3. Add fit explanations.
4. Add evidence-backed pros and cons.
5. Add Proof Mode.
6. Add shareable comparison links.
7. Add saved comparisons.
8. Commit and push.

### Phase 8 — Authentication and saved workspace

1. Add Supabase auth.
2. Add lightweight profiles.
3. Add saved agents.
4. Add saved searches.
5. Add saved comparisons.
6. Add basic preferences.
7. Verify RLS and server/client boundaries.
8. Commit and push.

### Phase 9 — Mission Builder and operations

1. Build structured mission creation.
2. Add objective, selected agent, permissions, expiry, and success criteria.
3. Add mission state machine.
4. Add Active Missions dashboard.
5. Add activity timeline.
6. Add permission history.
7. Add pause/revoke controls only where truly supported.
8. Add Mission Receipt data model.
9. Commit and push.

### Phase 10 — Real wallet and activation

1. Start with wallet connection and network checks.
2. Select the first documented BSC testnet activation path.
3. Show the exact permission scope.
4. Require explicit user approval.
5. Submit the real transaction/hire action.
6. Poll for the actual result.
7. Link to the explorer.
8. Store the real receipt.
9. Mark completed only from verified result data.
10. Add Altana sessions/caps/expiry/revoke only if the BSC path is proven.
11. Commit and push.

### Phase 11 — Quality and security

1. Typecheck.
2. Lint.
3. Unit-test normalization, ranking, intent validation, and mission states.
4. Integration-test live API paths.
5. Test unavailable/error states.
6. Test Supabase RLS.
7. Verify service keys never reach the browser.
8. Verify no private keys are stored.
9. Verify model output cannot choose arbitrary addresses/calldata.
10. Run a clean-browser end-to-end test.
11. Commit and push.

### Phase 12 — Submission and public handoff

1. Deploy production Vercel URL.
2. Verify from a clean browser/device.
3. Prepare demo account instructions.
4. Capture real explorer links.
5. Document all sources and evidence.
6. Document implemented versus unavailable capabilities.
7. Prepare the four-category coverage proof.
8. Prepare optional Altana/TermiX/PancakeSwap evidence.
9. Commit and push final submission materials.

## Commit and testing policy

We will not wait until the end to test.

### Push checkpoints

- `chore: initialize Noria project`
- `feat: add live agent ingestion`
- `feat: add agent discovery vertical slice`
- `feat: add deterministic ranking`
- `feat: add AI concierge`
- `feat: add comparison and proof mode`
- `feat: add saved workspace`
- `feat: add missions and permission history`
- `feat: add verified activation flow`
- `test: harden end-to-end flow`
- `chore: prepare hackathon submission`

Each checkpoint must include:

- Passing relevant tests
- A clean git status
- A pushed commit
- A usable Vercel preview when the frontend changes

### First testable milestone

The first meaningful preview is the real discovery vertical slice:

> Live 8004scan agents → category filters → Agent Passport → evidence links.

No fake cards or placeholder “success” states will be used to reach the preview.

---

## Model and usage routing

- Luna for planning, normal coding, and straightforward fixes.
- SOL only for architecture, difficult integrations, security-sensitive code, debugging, and final review.
- Gemini for Noria runtime intent parsing/explanations.
- Groq only as an optional runtime fallback.
- Never use a model to invent factual agent data or authorize transactions.

## Build estimate

- Focused engineering: approximately 25–45 active hours.
- First testable preview: after the ingestion/discovery vertical slice.
- Full judge-max v1: a focused multi-day campaign, with the activation integration as the main uncertainty.
